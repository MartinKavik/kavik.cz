GTKWave has been the default open-source waveform viewer for over two decades. It earned that position honestly: it was there first and it works. But the UI feels like it was designed for a world where CRT monitors were still standard. There are no precompiled Windows binaries for recent versions. macOS support is unreliable. Large waveform files can eat gigabytes of RAM and stall the UI. And if you try to file a bug, you will find an issue tracker where many things have been reported but few have been fixed recently.

[NovyWave](https://github.com/NovyWave/NovyWave) started from that frustration. It is an open-source waveform viewer built as a modern alternative — desktop app, cross-platform, with gamer-style WASD controls for navigating waveforms. The idea is not complicated: keep waveform debugging fast enough for daily professional use, but approachable enough that you do not need a wiki to add your first signal.

I built it on MoonZoon and Tauri — a single Rust codebase that compiles the frontend to WebAssembly, runs a native backend for file parsing and plugin hosting via Wasmtime, and wraps into a Tauri desktop app. Minimal JavaScript glue, no Electron. This post covers how user research and public issue tracker analysis shaped what gets built on top of that foundation.

## Three conversations that changed my priorities

I spent a cycle doing two things in parallel: reading public issue trackers to find where waveform viewer users get stuck, and replying to people who emailed me directly about NovyWave. The issue trackers told me what was broken. The emails told me what it felt like.

<Note>Direct quotes below are anonymized and lightly edited for length. They are included because they expose workflow pain that issue trackers often miss.</Note>

**A physics researcher** working with RedPitaya (Zynq 7) boards on Windows/WSL — not an FPGA professional, they were careful to note. After upgrading GHDL, GTKWave 3.3.100 stopped handling newer `.ghw` files, so they switched to `.fst`. They liked NovyWave's auto-reload immediately. But analog visualization was the sore point: "height extensions feel wonky, and values are normalized to the current window — I cannot set limits manually." One workflow saver, two critical UX gaps.

**A developer evaluating alternatives** on macOS and WSL2 because GTKWave "seems to be losing steam." They could not find prebuilt binaries for their setup, while another viewer installed with a single `brew install` and just worked. The line that stuck: "Hardware users are very conservative types." I had been so focused on what NovyWave could *do* that I had not spent enough time on whether anyone could *get* it.

**A cross-platform tester** on Mac M1 and Hyprland Arch Linux. No blank screen on M1 this time — that was fixed. But the file dialog expected Linux-style paths (`/home`) on macOS. Files in `/tmp` would not show up; moving them to `/usr/local/share` worked. Once past that hurdle: "Dock to Bottom is great, binary/hex toggle is practical, keyboard flow is strong, and multiple dump comparison is a huge plus." On Hyprland, everything worked without the filesystem issue. Good product — if you could get past the first 30 seconds.

Three people, three setups, same pattern: the core viewer works, but the edges — installation, file picking, analog display — are where trust breaks.

## What the issue trackers confirmed

The emails told me what *felt* broken. The issue trackers told me it was not just three people — it was a pattern across the entire GTKWave user base. Here are the recurring pain clusters I found:

**Signal onboarding is unintuitive.** Adding signals is literally the first thing you do in a waveform viewer, and users keep reporting it is confusing ([GTKWave #368](https://github.com/gtkwave/gtkwave/issues/368), [#476](https://github.com/gtkwave/gtkwave/issues/476)). If this step feels broken, people assume the tool is broken.

**Performance and memory break flow.** Stalls and RAM spikes destroy iterative debugging. A 500MB VCD file should not require 3GB of RAM ([GTKWave #173](https://github.com/gtkwave/gtkwave/issues/173), [#438](https://github.com/gtkwave/gtkwave/issues/438)).

**Format and semantic edges still hurt.** Newer GHDL versions produce `.ghw` files that older GTKWave builds cannot parse correctly ([SourceForge bug #21](https://sourceforge.net/p/gtkwave/bugs/21/)). The physicist hit exactly this.

**Navigation is still too manual.** Jump-to-next-change is a daily operation, not a luxury ([vcdrom #27](https://github.com/wavedrom/vcdrom/issues/27)).

**Theming and visual comfort are inconsistent.** Long debug sessions need readable UI, and GTKWave's theming has been a known gap for years ([GTKWave #4](https://github.com/gtkwave/gtkwave/issues/4), [oss-cad-suite #186](https://github.com/YosysHQ/oss-cad-suite-build/issues/186)).

**Cross-platform polish blocks adoption.** macOS issues alone have accumulated dozens of reports ([GTKWave #43](https://github.com/gtkwave/gtkwave/issues/43), [#207](https://github.com/gtkwave/gtkwave/issues/207), [#269](https://github.com/gtkwave/gtkwave/issues/269), [#250](https://github.com/gtkwave/gtkwave/issues/250)). Desktop problems feel like product reliability problems.

**Packaging is a product feature.** If users cannot install confidently, they never evaluate the core UX ([GTKWave #486](https://github.com/gtkwave/gtkwave/issues/486), [#219](https://github.com/gtkwave/gtkwave/issues/219), [Homebrew discussion #2367](https://github.com/orgs/Homebrew/discussions/2367)).

**Extensibility demand is explicit.** Users want plugins and automation, not just UI controls ([GTKWave #308](https://github.com/gtkwave/gtkwave/issues/308), [#209](https://github.com/gtkwave/gtkwave/issues/209)).

The pattern is not a single missing feature. It is compounding friction across onboarding, scale, and platform reliability.

## What is already built

These conversations did not happen in a vacuum. A lot of the foundation was already in place — the interviews just confirmed which parts mattered and which had gaps.

Here is what NovyWave already does:

- **VCD, FST, and GHW format support** — the three formats that cover most VHDL, Verilog, and GHDL workflows. The physicist's `.ghw` problem with GTKWave does not apply here.
- **Multi-file waveform comparison** — load two or more dumps into the same session and compare them side by side. The tester called this "a huge plus," and it is genuinely one of the things that surprised people the most.
- **Gamer-style navigation** — W/S to zoom, A/D to pan, Q/E for cursor movement. Shift for acceleration. If you have ever played an FPS, you already know the controls.
- **Auto-reload via plugin** — change your simulation, NovyWave detects the updated file and reloads it. The physicist's favorite feature, and mine too.
- **Workspace persistence and plugin system** — `.novywave` config files for per-project state. The plugin system is built on WebAssembly (Wasmtime), so plugins are sandboxed and portable across platforms. This directly answers the extensibility demand from the issue trackers ([GTKWave #308](https://github.com/gtkwave/gtkwave/issues/308), [#209](https://github.com/gtkwave/gtkwave/issues/209)) — users want automation, not just UI controls, and WASM plugins are how NovyWave delivers that.
- **Cross-platform desktop app** — built with Tauri, with builds for Linux (AppImage, .deb, .rpm), macOS (DMG), and Windows (MSI, NSIS).
- **Dark and light themes, flexible layouts** — including the "Dock to Bottom" layout the tester liked.
- **Browser and desktop modes** — NovyWave runs as a Tauri desktop app or as a browser app via the MoonZoon backend. The physicist's WSL scenario is a perfect example: run the backend in WSL, open `localhost` in a Windows browser — no desktop app installation needed. Also works for remote servers and team sharing over the network.
- **Signal state rendering** — Z (high-impedance), X (unknown), U (uninitialized), and N/A states already display with distinct colors and sizing. This came from the format compatibility research ([SourceForge bug #21](https://sourceforge.net/p/gtkwave/bugs/21/)).
- **Peak-preserving decimation** — zooming out on large traces keeps short events visible instead of losing them to sub-pixel averaging. Motivated by the performance cluster ([GTKWave #173](https://github.com/gtkwave/gtkwave/issues/173), [#438](https://github.com/gtkwave/gtkwave/issues/438)).
- **Jump to next/previous transition** — keyboard shortcut to jump between signal changes. The "navigation is too manual" issue tracker finding ([vcdrom #27](https://github.com/wavedrom/vcdrom/issues/27)) is already partially addressed.
- **Example projects for five HDLs** — ready-to-run examples for VHDL, Verilog, SpinalHDL, Amaranth, and Spade, so NovyWave is not tied to one ecosystem.

<Note>The auto-reload feature is not hardcoded into NovyWave's core. It is a WASM plugin called `reload_watcher` that monitors the filesystem and requests reloads. This is a deliberate design choice — the plugin system should carry its weight, and auto-reload is proof that it can.</Note>

## What I am fixing before I would feel good shipping this

Here is what is left. Not a roadmap — more like the list I keep looking at when I ask myself "would I recommend this to the physicist?"

### Analog signal rendering

This one goes directly to the physicist's feedback: "height extensions feel wonky, values normalized, cannot set limits." NovyWave's backend already parses Real/float values from waveform files, but the frontend renders them as digital rectangles with text — no line charts, no Y-axis. The plan is to add polyline or step-function rendering for analog signals, with a Y-axis scale and user-settable min/max limits. This is a significant addition, so the initial version will focus on getting basic line rendering working with reasonable defaults — a best-effort starting point that can be refined based on feedback.

### Signal row height resizing

Signal rows are currently fixed at 30 pixels. For analog traces you need vertical space to read values — the physicist's feedback makes that clear. The goal is drag-to-resize on row dividers, with per-signal heights stored in the workspace config. Analog signals would get a taller default.

### Signal grouping and coloring

The selected variables panel is currently a flat list. Past about twenty signals, it becomes hard to find anything — exactly the onboarding friction reported in [GTKWave #368](https://github.com/gtkwave/gtkwave/issues/368) and [#476](https://github.com/gtkwave/gtkwave/issues/476). Named collapsible groups with drag reorder and per-signal or per-group color assignment would bring structure to larger designs. Colors would be reflected in the waveform rendering.

### Named markers / time bookmarks

Jump-to-transition exists, but there is no way to bookmark important time points. This addresses the "navigation is too manual" cluster ([vcdrom #27](https://github.com/wavedrom/vcdrom/issues/27)) and the extensibility demand ([GTKWave #308](https://github.com/gtkwave/gtkwave/issues/308)). Named markers rendered as labeled vertical lines on the waveform, with keyboard shortcuts for add/next/prev, stored in the workspace config.

### File picker platform roots

Interview C — the macOS M1 tester — was blocked on first use because the file picker showed `/home` instead of `/Users`. Files in `/tmp` were invisible. This is a first-minute blocker that makes every other feature invisible. macOS needs `/Users`, `~/Desktop`, `~/Downloads`, `/Volumes`. Windows needs clean drive letter handling. And a clear "no waveform files here" empty-state message when a directory has no supported files.

<Note>These five items trace directly to the user research and issue tracker findings above. Each one addresses friction that real users reported — not speculative features.</Note>

## What this comes down to

Three conversations taught me more about what NovyWave needs than months of reading issue trackers alone. The tool works — the feedback confirmed that. What it needs now is the kind of care that turns "works" into "I trust this." Reliable file picking. Analog traces that behave. Installation that does not require workarounds.

If you want to try it or if you have thoughts of your own, the project is on [GitHub](https://github.com/NovyWave/NovyWave). I am not hard to reach.
